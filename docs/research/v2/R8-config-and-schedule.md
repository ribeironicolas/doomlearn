# R8: config and schedule for doomlearn v2

Repo pins of the reference clones (all under `scratchpad/phase2/repos/`, read only): opencode `3884062`, codex `3b6ab34`, orca `4735ecef`, ai-memory `76af077`.

## Question

How should doomlearn v2 hold its configuration? The owner's requirements are:
- one config that both a file and the PWA can edit,
- a provider (claude or codex), model and effort for each agent stage,
- control over when the worker runs: allowed windows or quiet hours, pause, pause until, daily cap and buffer target,
- usage and limits visible in the PWA.

This note also covers the file format, validation, precedence, reload, safe edits from the UI, secrets and the schedule model.

## Findings (with evidence)

### F1. Today's config is thin
- `src/data.ts` does a shallow spread of `config.json` over the defaults, with a per-stage merge for `claude`. There is no validation. The file is read once in `openData()`, and the defaults file is written on first run (`~/projects/doomlearn/src/data.ts` lines 38-56).
- The keys are `bufferTarget` 10, `dailyClipCap` 15, `port` 8443, `zerotierIp` and `claude.{extract,script,verify,split,scene}.{model,effort}` (README.md "config.json" table).
- A long list of tunables is hard-coded: the 60 s Clip cap, the word budget, retries, the claude timeout of 10 min, the rate-limit wait of 15 min, the ladder days, and the voice (`architecture-now.md` section 6).
- Standing decisions that constrain this design:
  - Bind only to localhost and the ZeroTier IP, with mkcert TLS.
  - Subscription login, no API key.
  - Model and effort per stage.
  - Buffer 10 and cap 15 are provisional.
  - `DOOMLEARN_HOME`.

### F2. How the mature agent CLIs store config
| | opencode | codex |
|---|---|---|
| Format | JSON or JSONC (`opencode.jsonc`, `opencode.json`, `config.json`), parsed with `jsonc-parser` and `allowTrailingComma` (`packages/opencode/src/config/parse.ts` L8-31, `config.ts` L141) | TOML (`~/.codex/config.toml`). `--strict-config` rejects unknown fields (`codex exec --help`) |
| Editor schema | Each file is seeded with `"$schema": "https://opencode.ai/config.json"` (`config.ts` L245-268). The schema is generated from code (`script/schema.ts`: `Schema.toJsonSchemaDocument` and `allowComments: true`) | A checked-in `codex-rs/core/config.schema.json`, generated by `just write-config-schema` from the Rust `schemars` derive (`justfile` L173). `deny_unknown_fields` is set on profiles (`codex-rs/config/src/profile_toml.rs`, via ctx7 `/openai/codex`) |
| Validation errors | Every issue is listed with its path. A JSONC syntax error prints the line, the column and a caret (`parse.ts` L8-60) | Strict mode is opt-in |
| Layering | Several layers: global, custom (`OPENCODE_CONFIG`), project, `.opencode` dirs and remote, deep-merged with `remeda.mergeDeep` (`config.ts` L42, L413-443) | 8 layers, where higher layers override lower ones: managed, CLI `-c` flags, project, user profile, user, cloud-managed, system. `origins()` reports where each key came from, for the UI (`codex-rs/config/src/loader/README.md`, via ctx7) |
| Secrets | `{env:VAR}` and `{file:path}` substitutions inside the config text (`variable.ts` L33-40) | Auth is kept separately (`docs/authentication.md`) |
| UI write-back | `updateGlobal` patches the file. For `.jsonc` it uses `jsonc-parser` `modify`/`applyEdits`, which keeps comments. It **decodes and validates the result before writing**, writes only if the text changed, then invalidates the cache (`config.ts` L656-679) | Atomic writes via `tempfile::NamedTempFile` then `.persist()` (`codex-rs/cloud-config/src/cache.rs` L166-193) |

ai-memory and Orca also use TOML for user config, with profiles (`ai-memory/README.md` L224, L383).

Summary: JSON or JSONC with a `$schema` key is the TypeScript-ecosystem pattern, and TOML is the Rust one. Both generate the schema from code and never write it by hand.

### F3. Zod v4 covers schema, defaults, errors and JSON Schema
- `z.toJSONSchema(schema, { io: "input" })` produces the **input** shape, where keys with defaults are optional. That is the right shape for a file the user only partly fills. `.meta({ description })` is copied into the JSON Schema, so editors show it on hover. The default target is draft 2020-12. (ctx7 `/colinhacks/zod/v4.3.6`, `json-schema.mdx`)
- `z.prettifyError(err)` gives a readable error for the CLI. `z.treeifyError(err)` gives a per-field tree that the PWA form can show under each field. (`error-formatting.mdx`)
- In Zod 4, `.default()` short-circuits on `undefined`, and defaults inside nested objects are applied. A group therefore needs `.prefault({})` (or `.default({})` with a full value) so that `{}` fills the whole tree. (https://zod.dev/v4/changelog, sections ".default() changes" and ".prefault()")
- This replaces the hand-written per-stage merge in `data.ts`: `ConfigSchema.parse(fileJson)` returns the full typed config with every default filled.

### F4. Provider effort values differ
- `claude --effort` accepts `low, medium, high, xhigh, max` (local `claude --help`).
- Codex `ReasoningEffort` is `none, minimal, low, medium, high, xhigh, max, ultra, persistent`, plus `Custom(String)` (`codex-rs/protocol/src/openai_models.rs` L60-73). Codex takes it as `-c model_reasoning_effort="low"` and the model as `-m` (local `codex exec --help`; ctx7 `/openai/codex` `sdk/typescript/src/exec.ts`).
- So the per-stage object should be a **discriminated union on `provider`**, with an effort enum for each provider. The PWA can then render the right dropdown.

### F5. Schedule patterns in self-hosted tools
- **Home Assistant time condition**: `after`, `before` and `weekday: [mon..sun]`. `after` is inclusive and `before` exclusive. When both are set and `after > before`, the window crosses midnight, so 22:00-06:00 works. (https://www.home-assistant.io/docs/scripts/conditions/)
- **qBittorrent bandwidth scheduler**: one `start` and `end` time plus a day selector (every day, a single day, weekdays or weekend). A 30 s timer checks the window, and `start > end` is handled by swapping and inverting (`src/base/bittorrent/bandwidthscheduler.cpp` L48-100, fetched raw from GitHub master).
- **Orca automations**: triggers are presets (`hourly`, `daily`, `weekdays`, `weekly`), 5-field cron or RRULE, plus `--disabled` (`orca/skill-guides/orca-cli/references/automations.md`). Cron and RRULE describe *when to start* something. doomlearn's worker is a loop that is always on, so it needs a *window in which it may run*. Windows fit better than cron.
- doomlearn already has the pause machinery. The worker waits until `resetsAt` after a rate limit (`architecture-now.md` section 3, a standing decision). It ticks every 5 s when idle (`src/main.ts`), so checking a window at the start of each tick costs nothing. That matches qBittorrent's 30 s poll.

### F6. Usage and limit data available
- Claude: `claude_calls` already logs cost, tokens, duration, stage and `retry_at` for every call (a standing decision). The 5 h and 7 d subscription percentages (`rate_limits.five_hour/seven_day.used_percentage`) are documented **only in the statusline JSON input** of interactive Claude Code (https://code.claude.com/docs/en/statusline, via ctx7 `/websites/code_claude`). I found no evidence that `claude -p --output-format json` returns them. **Not verified.**
- Codex: the app-server protocol has `RateLimitWindow { used_percent, window_duration_mins, resets_at }` and `CreditsSnapshot` (`codex-rs/app-server-protocol/src/protocol/v2/account.rs` L752-775). Whether `codex exec --json` emits them per call is also **not verified**.
- Conclusion: config can hold *thresholds* such as "stop at X% used" only if a usage source exists. Building that usage source belongs to the usage/limits research, not to config.

### F7. Atomic write
- Writing a temp file in the same directory and then calling `rename()` replaces the target atomically on POSIX. A reader sees either the old file or the new one, never half of one. (rename(2), https://man7.org/linux/man-pages/man2/rename.2.html)
- Codex does the same through `NamedTempFile::persist` (F2).
- doomlearn has two writers: the CLI process and the server. The file is small and edits are rare, so validate, then write `config.json.tmp`, then `rename` is enough. No lock is needed.

## Recommendation for doomlearn v2

**R1. Format: plain `config.json` with `"$schema": "./config.schema.json"`, without comments.**
- The PWA rewrites the file. With plain JSON, `JSON.stringify` round-trips safely, so we don't need `jsonc-parser` patching (opencode needed 30+ lines for it, `config.ts` L141-160).
- Key descriptions live in the schema through `.meta({ description })` and show on hover in VS Code and Zed. That replaces comments.
- TOML would add a parser dependency and need a second schema tool (Taplo) to get autocomplete.
- Tradeoff: no comments in the file. If the owner wants them, switch to JSONC and patch with `jsonc-parser` `modify`, as opencode does. See the open questions.

**R2. One Zod schema is the source of truth, in `packages/core/src/config.ts`.**
- `parse(file)` fills the defaults (F3).
- A script `pnpm config:schema` writes `config.schema.json` with `z.toJSONSchema(ConfigSchema, { io: "input" })`.
- CI checks that the schema is up to date (`git diff --exit-code`), the same way codex runs `just write-config-schema`.
- On first run, copy the schema into `DOOMLEARN_HOME` next to `config.json`, so `$schema` resolves offline.

**R3. Precedence: defaults, then `config.json`, then a small fixed set of env vars.**
- The only env vars are `DOOMLEARN_HOME` (existing) and `DOOMLEARN_PORT`/`DOOMLEARN_HOST`, which are useful for CI or smoke runs on a temp home.
- No layers, profiles or `{env:}` substitution: there is one Learner and one file. Codex has 8 layers and opencode 6 because they serve projects and enterprises, which doomlearn does not.
- The PWA shows which value is "overridden by env" in read-only form. This is a light version of codex `origins()`.

**R4. Reload instead of restart.** The core holds `config` behind a getter.
- The **worker reads `getConfig()` at the start of every tick**. Each tick it checks `config.json`'s `mtime` with one cheap `stat`, so hand edits are picked up within 5 s.
- If the file is invalid, the worker keeps the last good config, logs `z.prettifyError`, and the PWA shows a banner. It never crashes.
- A PWA save goes through `PUT /api/config` (Hono). The handler:
  1. parses the body with the schema (on failure it returns 422 with the `z.treeifyError` result),
  2. strips values equal to the default (optional),
  3. writes `config.json.tmp`, then calls `rename`,
  4. swaps the in-memory config,
  5. answers `{ config, restartRequired: string[] }`.
- `server.*` changes need a process restart, because sockets and TLS are bound at start. The PWA says so, and v2 does not restart itself, which follows the standing decision that the owner starts the process.

**R5. Secrets: there are none, and the schema enforces that.**
- Claude and Codex use their own CLI logins (a standing decision). API keys are never doomlearn config.
- `GET /api/config` can therefore return the whole file.
- If a provider ever needs a key, it is read from the provider's own env (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`) and is documented, not stored.

**R6. Schedule = allowed windows plus pause, checked at the start of the tick.**
- Keep `worker.paused` (manual switch) and `worker.pausedUntil` (ISO time, cleared automatically once it passes), plus `schedule.windows`.
- An empty `windows` list means "always allowed".
- A window is `{ days, start: "HH:MM", end: "HH:MM" }` with Home Assistant semantics: start inclusive, end exclusive, and the window crosses midnight when `start > end`.
- Quiet hours are just the complement, expressed as windows. Don't add a second concept.
- Times use the Mac's local timezone. An optional `timezone` field can be added later if a non-Mac host needs it.
- When the worker is outside a window, it **finishes the running stage** and does not start the next one. Stages are already checkpointed to disk, so stopping mid-stage is never needed.
- `/api/status` reports `blockedBy: "paused" | "pausedUntil" | "window" | "rateLimit" | "dailyCap" | "bufferFull" | null` and `nextRunAt`.

**R7. Paste-ready schema sketch** (Zod 4):
```ts
import { z } from 'zod';

const Time = z.string().regex(/^([01]\d|2[0-3]):[0-5]\d$/, 'HH:MM, 24h');
const Day = z.enum(['mon', 'tue', 'wed', 'thu', 'fri', 'sat', 'sun']);

/** Which CLI runs a stage, with that CLI's own model and effort vocabulary. */
const StageAgent = z.discriminatedUnion('provider', [
  z.object({
    provider: z.literal('claude'),
    model: z.string().meta({ examples: ['opus', 'sonnet', 'haiku'] }),
    effort: z.enum(['low', 'medium', 'high', 'xhigh', 'max']),
  }),
  z.object({
    provider: z.literal('codex'),
    model: z.string().meta({ examples: ['gpt-5.5'] }),
    effort: z.enum(['minimal', 'low', 'medium', 'high', 'xhigh']),
  }),
]);
const claude = (effort: 'low' | 'medium') => ({ provider: 'claude' as const, model: 'opus', effort });

export const ConfigSchema = z.object({
  $schema: z.string().optional(),
  agents: z.object({
    stages: z.object({
      extract: StageAgent.default(claude('medium')),
      script: StageAgent.default(claude('low')),
      verify: StageAgent.default(claude('low')),
      split: StageAgent.default(claude('low')),
      scene: StageAgent.default(claude('low')),
    }).prefault({}),
    timeoutMinutes: z.number().int().min(1).default(10), // today hard-coded
  }).prefault({}),
  worker: z.object({
    paused: z.boolean().default(false),
    pausedUntil: z.iso.datetime({ offset: true }).nullable().default(null),
    schedule: z.object({
      windows: z.array(z.object({
        days: z.array(Day).min(1).default(['mon', 'tue', 'wed', 'thu', 'fri', 'sat', 'sun']),
        start: Time, // inclusive
        end: Time,   // exclusive; start > end crosses midnight
      })).default([]), // [] = always allowed
    }).prefault({}),
    bufferTarget: z.number().int().min(0).default(10),
    dailyClipCap: z.number().int().min(0).default(15),
  }).prefault({}),
  server: z.object({
    hosts: z.array(z.string()).default(['127.0.0.1']), // add the ZeroTier/LAN IP here
    port: z.number().int().min(1024).max(65535).default(8443),
    tls: z.object({ cert: z.string(), key: z.string() }) // relative to DOOMLEARN_HOME
      .default({ cert: 'tls/cert.pem', key: 'tls/key.pem' }),
  }).prefault({}),
  narration: z.object({
    voice: z.string().default('faber-x1.25'),
    language: z.string().default('pt-BR'),
  }).prefault({}),
  paths: z.object({
    sources: z.string().default('sources'),
    jobs: z.string().default('jobs'),
    clips: z.string().default('clips'),
  }).prefault({}),
}).strict(); // unknown keys are errors (typos), like codex --strict-config
export type Config = z.output<typeof ConfigSchema>;
```

Notes on the sketch:
- `zerotierIp` becomes the general `server.hosts`, since ZeroTier is one option among several. Migrate an old `zerotierIp` into `hosts` once, at load.
- The keys of `agents.stages` match the `AgentStages` keys in `src/agent.ts`.
- Under `strict()`, migration code must rename old keys (`claude`, `zerotierIp`) **before** parsing. Otherwise every v1 file fails.

**R8. Which keys the PWA may edit, and when they take effect:**

| Group / key | Editable in PWA | Takes effect |
|---|---|---|
| `worker.paused`, `pausedUntil`, `schedule.windows`, `bufferTarget`, `dailyClipCap` | yes (main "Worker" screen) | next tick (at most 5 s) |
| `agents.stages.*` (provider, model, effort), `timeoutMinutes` | yes | the next stage that starts. A running call keeps its settings |
| `narration.*` | yes | Clips whose narration stage has not run yet. Existing Clips are unchanged |
| `server.hosts`, `server.port`, `server.tls.*` | **read-only** in the PWA (a wrong value cuts off the phone), file only | restart |
| `paths.*` | **read-only**, file only | restart. Changing paths moves no data |

Usage and limits are **not config**. Show them on the Worker screen from `claude_calls` aggregates (today, 5 h and 7 d sums, last `resetsAt`). Add provider percentages only once F6 confirms a source.

## Open questions
1. **JSON or JSONC.** Does the owner want comments in `config.json`? If so, JSONC with `jsonc-parser` patching (opencode). Otherwise plain JSON (the recommendation).
2. **What the schedule gates.** Should it gate only agent stages (credits) or the whole worker (also TTS and render: fan noise and battery at night)? The recommendation gates the whole worker for simplicity. The owner's phrase was "when the agents run".
3. **Usage source.** Can `claude -p` or `codex exec --json` return the subscription 5 h and 7 d usage per call? This is unverified (F6). It decides whether a `worker.stopAtUsagePercent` key can exist. Hand it to the usage/limits research.
4. **Model names.** Codex model names change often. Should `model` stay a free string with `examples` (as recommended), or should doomlearn validate it against the provider's model list at startup?
5. **Hard-coded tunables.** Should the hard-coded tunables in `architecture-now.md` section 6 (Clip length, word budget, retries, ladder) become config in v2? The recommendation is no, except `timeoutMinutes`. They are product rules, not user preferences, and Simplicity First applies.
6. **v1 migration.** Should doomlearn rewrite the old `config.json` to the v2 shape automatically (with a `.bak`), or only map it in memory?
