# R2 — Reference repos: how agent projects structure themselves for users and contributors

Clones (depth 1, read-only, 2026-10-08) live under `scratchpad/phase2/repos/{ai-memory,orca,opencode,codex}`. Below, `$R` stands for that directory.

## Question

How do four well-regarded open-source agent projects (akitaonrails/ai-memory, stablyai/orca, sst/opencode, openai/codex) handle repo layout, stack, config (format, schema, env override, per-provider model/effort), docs, CI/release, provider usage/limits, and license? Which patterns should doomlearn v2 copy (pnpm monorepo, Vite+React PWA, Hono server, Claude+Codex per-stage model/effort, AGPL, self-hosted, Mac-first), and which should it avoid?

### 2. How the projects show provider usage and limits (owner wants "see my credit limits from the PWA")

- **Claude, preferred source (free):** Claude Code (>=2.1.80) passes `rate_limits` with `five_hour` and `seven_day` windows (`used_percentage`, `resets_at`) to the statusLine command on every turn. Orca captures this through a generated statusline script that POSTs to its local server (`$R/orca/src/shared/claude-statusline-rate-limits.ts:1-25`, `src/main/claude/statusline-script.ts`). The comment explains why: the data rides on Messages API responses, so reading it costs no usage-endpoint budget.
- **Claude, polled source:** `GET https://api.anthropic.com/api/oauth/usage` with the subscription OAuth token and the header `anthropic-beta: oauth-2025-04-20`. It returns `five_hour`, `seven_day`, per-model weekly `limits[]`, `extra_usage` and `spend` (`$R/orca/src/main/rate-limits/claude-oauth-usage-request.ts:13-82`). The token comes from the Claude credentials file or the macOS Keychain (`claude-oauth-credentials.ts:123`, `claude-active-usage-fetch.ts`). This endpoint is **undocumented** and 429s easily. Orca polls every 15 min by default, never more often than every 30 s, debounces manual refreshes to 5 min, honours Retry-After and backs off per failure (`src/main/rate-limits/service/service-types.ts:96-102`, `service-fetch-policy.ts:40-70`). Orca also has a fallback that runs `claude /usage` in a hidden PTY and parses the output (`claude-pty-usage-parser.ts`, `claude-cli-usage-fetch.ts`).
- **Codex:** Codex itself exposes JSON-RPC `account/rateLimits/read` and the `account/rateLimits/updated` notification over `codex app-server`. `RateLimitSnapshot` contains `primary` and `secondary` windows (`usedPercent`, `windowDurationMins`, `resetsAt`) plus `credits` and `planType` (`$R/codex/codex-rs/app-server-protocol/schema/typescript/v2/RateLimitSnapshot.ts`, `RateLimitWindow.ts`). Orca spawns `codex app-server` and sends `account/rateLimits/read` (`$R/orca/src/main/rate-limits/codex-rpc-rate-limit-probe.ts:222`). It falls back to `https://chatgpt.com/backend-api/wham/usage` (`codex-backend-usage-client.ts:68`).
- **Historical cost/tokens:** Orca scans `~/.claude/projects` transcripts and `~/.codex/sessions` rollouts, then applies per-model pricing tables (`src/main/claude-usage/transcript-file-discovery.ts:6-7`, `src/main/codex-usage/codex-model-pricing.ts`). doomlearn does not need this, because every call is already logged to `claude_calls` (a standing decision).
- **Provider abstraction for usage:** Orca normalizes every provider into one `ProviderRateLimits` / `RateLimitWindow` type (`src/shared/rate-limit-types`) and keeps one fetcher file per provider under `src/main/rate-limits/`.

### 3. What makes each one pleasant (or not) to contribute to

- **ai-memory:** two docs tables, one for users and one for contributors, each row with a single-sentence purpose. The design-decisions doc records options with pros and cons. The gates are one copy-paste block and need no env vars ("The build is self-contained", `CONTRIBUTING.md:44-46`). `CLAUDE.md` is just `@AGENTS.md` plus a comment explaining why (`$R/ai-memory/CLAUDE.md`). The downside is size: a 621-line README and 636-line AGENTS.md are heavy reading.
- **orca:** the PR template asks for ELI5, Why and Visual Proof. Its `// Why:` comment convention makes non-obvious code self-explaining (seen throughout `rate-limits/`). The downside is scale: 100+ workflows, ~150 npm scripts and a cloud relay are not reproducible for a contributor.
- **opencode:** the `$schema` URL gives editor autocomplete. It has an issue-first policy, Conventional Commit titles with a package scope, and a short PR template. Its domain glossary in `CONTEXT.md` mirrors doomlearn's. The downside is complexity: Bun, Effect, Solid and SST infra mean high onboarding cost, and the root `test` script deliberately fails ("do not run tests from root").
- **codex:** the schema is generated from code, drift-tested and released as an artifact, and profiles make variants explicit. The downside is that it is closed to external PRs and uses Bazel. Neither suits a community side project.

## Recommendation for doomlearn v2

### Copy

1. **Layout `apps/` + `packages/`** as in the owner's reference monorepo's `pnpm-workspace.yaml` (`apps/*`, `packages/*`, `catalog:`). For doomlearn this would be `apps/server` (Hono), `apps/web` (Vite PWA), `apps/cli`, `packages/core` (pipeline, queue, SRS), `packages/db` (Drizzle), `packages/agents` (Claude/Codex runners), `packages/config`. Use a pnpm `catalog` for shared versions, as in opencode `package.json` `workspaces.catalog` and the owner's reference monorepo. Python/TTS stays in a non-JS folder outside the JS graph, the way Orca isolates `mobile/` (`$R/orca/pnpm-workspace.yaml`).
2. **pnpm supply-chain settings** from codex/orca: `minimumReleaseAge`, an `allowBuilds` allowlist, `strictDepBuilds` (`$R/codex/pnpm-workspace.yaml`, `$R/orca/pnpm-workspace.yaml`).
3. **One config file, schema-validated, loaded once.** Use `doomlearn.config.jsonc` (or TOML) in `DOOMLEARN_HOME`, validated by Zod, with a JSON Schema generated from the Zod schema and committed, plus a test that fails on drift (codex `justfile:172`, `schema_tests.rs:14`). Use a `$schema` key for editor autocomplete (opencode `config.mdx:16`). Precedence would be defaults < file < `DOOMLEARN_*` env, read once into an immutable object (ai-memory `config.rs:1-7`, which records why the project has a single read path).
4. **Per-stage agent settings modelled on codex profiles and opencode agents.** Each stage sets `{ provider: "claude"|"codex", model, effort }`, with named presets ("profiles"/"variants") to swap them all at once (codex `ConfigProfile`, opencode `models.mdx:108-185`). Effort is a provider-validated string, not a global enum (codex `ReasoningEffort` is `string, minLength 1`).
5. **Limits panel in the PWA** using a normalized `RateLimitWindow {usedPercent, resetsAt, windowMins}` type (Orca `src/shared/rate-limit-types`). For Codex, use `codex app-server` → `account/rateLimits/read`, the documented protocol (`codex-rs/app-server-protocol/.../RateLimitSnapshot.ts`). For Claude, first record whatever `claude -p` already returns on rate-limit errors (`resetsAt`, a standing decision). Polling the OAuth usage endpoint should be opt-in, with Orca's 15-minute default, Retry-After handling and backoff (`service-types.ts:96-102`).
6. **Docs set:** a README with a users table and a contributors table (ai-memory `README.md:567-612`), `CONTRIBUTING.md` with exact gate commands that need no secrets (ai-memory `CONTRIBUTING.md:42-62`), `docs/adr/` (already present), `CHANGELOG.md` in Keep a Changelog format with an `[Unreleased]` merge gate (ai-memory `CONTRIBUTING.md:114-128`), `SECURITY.md`, and `CLAUDE.md` = `@AGENTS.md` (ai-memory `CLAUDE.md`).
7. **GitHub hygiene:** YAML issue forms, a short PR template (Closes #, why, how verified, screenshot for UI; opencode and orca templates), CODEOWNERS, dependabot, and gitleaks secret scanning (ai-memory `.github/workflows/secret-scan.yml`). The secret scan matches the owner's one public-repo bar (a standing decision).
8. **CI kept small:** one `ci.yml` running lint, typecheck, test and build on `macos-latest` and `ubuntu-latest`, plus a tag-triggered release. That is roughly the size of ai-memory's 6 workflows. Tests must fake `claude`/`codex` binaries so CI never needs a subscription.
9. **Conventions:** `// Why:` comments for non-obvious decisions (Orca `rate-limits/*`). Conventional Commit PR titles with a package scope (opencode `CONTRIBUTING.md:212-236`) fit doomlearn's existing commit rule (a standing decision).

### Avoid

- Orca-scale CI (100+ workflows) and a scripts sprawl of ~150 npm scripts (`$R/orca/.github/workflows`, `package.json`).
- Bun, Effect and Bazel toolchains (opencode, codex). They are unneeded and the owner chose pnpm + Hono.
- A root `test` script that refuses to run (`$R/opencode/package.json` `"test": "echo 'do not run tests from root' && exit 1"`). Use `pnpm -r test` instead.
- An 8-layer config precedence with remote and MDM layers (opencode `config.mdx:42-56`). doomlearn needs 3 layers.
- README sprawl (ai-memory, 621 lines). Keep the README short and link out.
- Closed contribution model and CLA (codex `docs/contributing.md:5`, `cla.yml`). They conflict with the goal of attracting contributors.
- Making the undocumented `api.anthropic.com/api/oauth/usage` a hard dependency. Orca carries many recovery and legacy-Keychain paths for it (`claude-active-usage-fetch.ts`, `claude-oauth-recovery.ts`), which shows how fragile it is.

## Open questions

1. Does `claude -p --output-format json` already include rate-limit windows in the success payload, or only `resetsAt` on errors? Verify against current Claude Code docs (context7) before designing the Claude half of the limits panel.
2. Should the Claude limits panel read the Keychain OAuth token and call the undocumented `/api/oauth/usage` endpoint? It works today (Orca ships it), but it is fragile and arguably beyond "subscription via `claude -p`" (a standing decision). This needs an owner decision.
3. Should the config file be JSONC (TS-native, `$schema` autocomplete) or TOML (codex/ai-memory style)? JSONC + Zod is recommended because the stack is all TS.
4. Should the Codex runner use `codex exec --json` (one-shot, mirrors `claude -p`) or a long-lived `codex app-server` (which also yields rate limits)? See R-topic on Codex CLI.
5. AGPL-3.0 (a standing decision) differs from all four references (MIT/Apache). That is fine for a self-hosted app, but the README should explain it and say whether a CLA or DCO is wanted. The recommendation is DCO or nothing, not a CLA.
6. Hono is not what opencode uses in its main server today (Effect HttpApi). The owner's Hono choice still stands. opencode's useful pattern is generating `openapi.json` from the server and generating the client SDK from it (`$R/opencode/packages/sdk/js/script/build.ts:10-48`). Should v2 do the same for the PWA client (hono-openapi or `@hono/zod-openapi`)?
